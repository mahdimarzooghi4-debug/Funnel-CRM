# طراحی فنی نخستین برش پیکربندی و پرونده‌ی CRM

- بک‌لاگ: CRM-DOM-01 و بخشی از CRM-DOM-02
- وضعیت: طرح و هسته‌ی داده در Sprint 09؛ PR پیش‌نویس
- migration: `20261018_01`

## مدل داده

| جدول | کاربرد | قید امنیتی/داده |
|---|---|---|
| `workspace_crm_settings` | مدل‌های کاری انتخاب‌شده برای Workspace و نسخه‌ی تنظیم | یک ردیف برای هر tenant؛ آرایه‌ی غیرخالی؛ RLS |
| `crm_pipelines` | قیف قابل‌تنظیم و مراحل آن برای نوع رکورد | کلید یکتا در هر tenant؛ مراحل غیرخالی؛ حداکثر یک قیف پیش‌فرض برای هر نوع؛ RLS |
| `crm_custom_field_definitions` | تعریف فیلدهای سفارشی نوع‌دار برای پرونده‌ها | کلید یکتا بر اساس tenant و نوع پرونده؛ گزینه فقط برای فیلد انتخابی؛ RLS |
| `crm_profiles` | پرونده‌ی شخص یا سازمان با مرحله‌ی چرخه‌ی عمر | تکیه بر `tenant_records` و پیوند سازمانی tenant-safe؛ RLS |

مدل کسب‌وکار با شناسه‌های توسعه‌پذیر ثبت می‌شود تا هر Workspace به یک دسته‌ی ثابت مجبور نشود. نقش و دامنه‌ی سازمانی مستقل از این تنظیم باقی می‌مانند. هر پروفایل فرد/سازمان به حساب ورود تبدیل نمی‌شود.

## ممیزی و حریم داده

تغییر تنظیم Workspace، قیف، تعریف فیلد و پروفایل در `audit_events` ثبت می‌شود. snapshot پروفایل فقط نوع پرونده و مرحله‌ی چرخه‌ی عمر را نگه می‌دارد و نام نمایشی در snapshot ممیزی کپی نمی‌شود. اتصال به سازمان، شناسه‌ی tenant را در کلید خارجی حمل می‌کند تا اتصال بین Workspaceها در پایگاه‌داده ناممکن باشد.

## شواهد آزمون

`tests/test_crm_profile_foundation.py` مقدار پیش‌فرض و تغییر تنظیم، ایجاد قیف/فیلد/پروفایل، یکتایی قیف پیش‌فرض، محدودیت مراحل و کلید فیلد، RLS، ارجاع سازمانی بین tenantها و شکل snapshot ممیزی را می‌آزماید.

## مرز این برش

این اسپرینت هسته‌ی tenant-safe داده را می‌سازد. مقداردهی و endpointهای مدیریتی هنوز به کنترل دسترسی منبع/اقدام نیاز دارند و در این PR در معرض API قرار نمی‌گیرند. اطلاعات تماس، تطبیق/ادغام رکورد تکراری، مقادیر فیلدهای سفارشی و قواعد رضایت و نگهداری داده در برش‌های بعدی طراحی می‌شوند؛ دامنه‌ی نهایی CRM را حذف نمی‌کنند.
