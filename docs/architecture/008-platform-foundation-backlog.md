# بک‌لاگ فنی پایه‌ی CRM فانل

- وضعیت: پیش‌نویس برای شروع پالایش فنی
- منبع دامنه: نقشه‌ی کسب‌وکاری CRM و تصمیم‌های فنی ۰۰۱ تا ۰۰۷
- دامنه‌ی نهایی محصول: همه‌ی ماژول‌های مصوب نقشه؛ این ترتیب اجرای مهندسی است و دامنه‌ی محصول نهایی را کم نمی‌کند.

## بسته‌ی پایه

| شناسه | کار فنی | وابستگی | معیار پذیرش |
|---|---|---|---|
| CRM-FND-01 | ساخت سرویس FastAPI ماژولار و قرارداد API نسخه‌دار | تصمیم ۰۰۱ | ماژول‌ها مرز روشن دارند؛ health/readiness و قرارداد OpenAPI قابل‌آزمون‌اند |
| CRM-FND-02 | مدل Workspace/Tenant و سازمان ریشه | تصمیم‌های ۰۰۲، ۰۰۳ و طراحی ۰۰۷ | هر tenant فضای کاری و سازمان ریشه‌ی مستقل دارد؛ ارجاع میان tenantها رد می‌شود |
| CRM-FND-03 | هویت، عضویت، نقش و دامنه‌ی سازمانی | تصمیم‌های ۰۰۳ تا ۰۰۶ | مجوز مؤثر بدون هر دو شرط نقش و دامنه صادر نمی‌شود؛ حالت تعریف‌نشده deny است |
| CRM-FND-04 | زمینه‌ی tenant در درخواست، تراکنش و RLS | تصمیم‌های ۰۰۲، ۱۱۸، ۱۴۱، ۱۴۲ | نقش runtime غیرمالک و فاقد BYPASSRLS است؛ آزمون pool reuse و خواندن/نوشتن cross-tenant ناموفق است |
| CRM-FND-05 | پایه‌ی داده و migration برای رکوردهای tenant-owned | طراحی ۰۰۷ | مالکیت tenant روی جداول و کلیدهای خارجی رعایت می‌شود؛ migration نسخه‌دار و آزمون‌پذیر است؛ برای تغییر مخرب مسیر بازیابی یا پیش‌روی ایمن مستند می‌شود |
| CRM-FND-06 | لاگ ممیزی برای عضویت، نقش، مجوز و تغییر ساختار سازمانی | تصمیم‌های ۰۰۳، ۰۰۵ و ۰۰۶ | عامل، زمان، دامنه و تغییر پیش/پس برای رویدادهای حساس قابل‌ردیابی‌اند |
| CRM-FND-07 | قرارداد پایه‌ی API/رویداد برای اتصال محصولات مشتری، از جمله محصولات فانل | تصمیم‌های اتصال و نسخه‌بندی | tenant، منبع، نسخه و شناسه‌ی هم‌بستگی مشخص‌اند؛ مجوز اتصال محدود به Workspace است |
| CRM-FND-08 | آزمون‌های امنیتی و بار برای مسیر پایه | تصمیم‌های ۰۰۲، ۰۰۶ و ۱۱۸ | آزمون‌های منفی جداسازی tenant و دامنه، همراه با سنجش بار ثبت و اجرا می‌شوند |

## ترتیب اجرا

1. قراردادهای هویت و زمینه‌ی tenant را تثبیت کن.
2. Workspace، ساختار سازمانی و نقش/دامنه را پیاده کن.
3. RLS و محدودیت‌های کلید خارجی tenant را در پایگاه‌داده فعال کن.
4. ممیزی، API/رویداد پایه و آزمون‌های cross-tenant را اضافه کن.
5. سپس مدل‌های دامنه و گردش‌کارهای همه‌ی ماژول‌های نقشه را به همین پایه متصل کن.

## شرط خروج از بسته‌ی پایه

- طراحی تفصیلی مدل داده، policyهای RLS و قرارداد API/رویداد برای بازبینی آماده باشد.
- آزمون‌های خودکار جداسازی tenant، نقش و دامنه روی PostgreSQL اجرا شوند.
- معیارهای پذیرش ماژول‌ها به بک‌لاگ فنی هر ماژول نگاشت شده باشند.
- مستندات نشان دهند همه‌ی قابلیت‌های مصوب برای عرضه‌ی کامل پوشش دارند؛ فازبندی فقط ترتیب ساخت داخلی را مشخص می‌کند.


## بک‌لاگ دامنه پس از بسته‌ی پایه

نگاشت قابلیت‌های کامل CRM به اپیک‌های دامنه در [بک‌لاگ ماژول‌های CRM](015-crm-domain-module-backlog.md) ثبت شده است. همه‌ی قابلیت‌های سند در دامنه‌ی محصول باقی می‌مانند؛ ترتیب وابستگی‌ها فقط برای ساخت داخلی است.
